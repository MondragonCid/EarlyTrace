# Auth & Admin Management

Feature group **F1: Authentication and RBAC** of EarlyTrace.
Covers logging in, registering, account status, instructor approval and password reset.

## 1. What it does

- **Registration:** students and instructors create their own account. Admin accounts can't be self-registered.
- **Login:** the backend checks the email and password and returns the user, without the password.
- **Account status:** every user is `PENDING`, `ACTIVE` or `INACTIVE`.
  - New **students** (and admins) start as `ACTIVE`.
  - New **instructors** start as `PENDING` until an admin approves them.
  - `PENDING` and `INACTIVE` users can't log in.
- **Instructor approval:** an admin approves a pending instructor (→ `ACTIVE`) or rejects them (→ `INACTIVE`).
- **Activate / deactivate:** an admin can turn any account on or off.
- **Password reset:** an admin sets a new password for a user.
- **Passwords are never sent back:** API responses never include `passwordHash`.

## 2. User fields

| Field | Type | Notes |
|---|---|---|
| `id` | Long | Generated by the database |
| `email` | String | Required, unique |
| `passwordHash` | String | Required. **Write-only:** accepted in requests, never returned |
| `fullName` | String | Required |
| `roleType` | `ADMIN` \| `INSTRUCTOR` \| `STUDENT` | Required |
| `status` | `PENDING` \| `ACTIVE` \| `INACTIVE` | Set by the backend on registration; any value sent by the client is ignored |
| `timestamp` | DateTime | `created_at`, set automatically when the user is created |

## 3. Endpoints

Base URL: `http://localhost:8080/api/users`

| Method | Path | Purpose |
|---|---|---|
| POST | `/postUser` | Register a new user |
| POST | `/login` | Log in |
| GET | `/getAllUsers` | List all users |
| GET | `/getUserById/{id}` | Get one user |
| PUT | `/updateUser/{id}` | Update a user (used for password reset) |
| PUT | `/updateStatus/{id}` | Approve, reject, activate or deactivate |
| DELETE | `/deleteUser/{id}` | Delete a user |

### POST `/postUser`: register

Request:
```json
{
  "fullName": "Juan Dela Cruz",
  "email": "juan@cit.edu",
  "passwordHash": "juanpass123",
  "roleType": "STUDENT"
}
```

Response `200`:
```json
{
  "id": 3,
  "email": "juan@cit.edu",
  "fullName": "Juan Dela Cruz",
  "roleType": "STUDENT",
  "status": "ACTIVE",
  "timestamp": "2026-11-22T09:00:00"
}
```

| Error | When |
|---|---|
| `409` | Email already registered |

### POST `/login`: log in

Request:
```json
{
  "email": "juan@cit.edu",
  "password": "juanpass123"
}
```

Response `200`: the user (same shape as above, never with the password).

| Error | When |
|---|---|
| `401` | Wrong email or password |
| `403` | Account is `PENDING` or `INACTIVE` |

### GET `/getAllUsers`: list users

Response `200`: an array of users. Used by the Admin Dashboard for counts, pending approvals and the user table.

### PUT `/updateUser/{id}`: update a user / reset password

The backend replaces **all four** fields, so always send the full user:

```json
{
  "email": "juan@cit.edu",
  "fullName": "Juan Dela Cruz",
  "roleType": "STUDENT",
  "passwordHash": "newpassword123"
}
```

Response `200`: the updated user. `404` if the user doesn't exist.

### PUT `/updateStatus/{id}`: change account status

Request:
```json
{ "status": "ACTIVE" }
```

| Action in the admin page | Status sent |
|---|---|
| Approve instructor | `ACTIVE` |
| Reject instructor | `INACTIVE` |
| Activate | `ACTIVE` |
| Deactivate | `INACTIVE` |

Response `200`: the updated user. `400` if `status` is missing, `404` if the user doesn't exist.

## 4. Rules

1. Only `STUDENT` and `INSTRUCTOR` can register through the app. Admin accounts are created directly (Postman or the database).
2. Students and admins start `ACTIVE`; instructors start `PENDING`.
3. `PENDING` and `INACTIVE` users can't log in.
4. `passwordHash` is never included in a response.
5. The frontend stores the logged-in user (id, name, email, role, status, never the password) in `localStorage` under `currentUser`.
6. Each page checks `currentUser.roleType` and shows a "log in as …" message to the wrong role.

## 6. Setup and testing

### Database update for existing users

Users created before `status` was added have no status. After starting the backend once (so the column is added), run:

```sql
USE earlytrace;
UPDATE users SET status = 'ACTIVE' WHERE status IS NULL;
```

### Postman

1. Start MySQL and the backend: `cd backend`, then `.\mvnw.cmd spring-boot:run`.
2. **Create an admin:** POST `http://localhost:8080/api/users/postUser`
   ```json
   { "fullName": "Admin", "email": "admin@earlytrace.com", "passwordHash": "admin12345", "roleType": "ADMIN" }
   ```
3. **Register a student and an instructor** the same way, with `roleType` `STUDENT` and `INSTRUCTOR`. The instructor's `status` is `PENDING`.
4. **List users:** GET `/getAllUsers`. No `passwordHash` appears.
5. **Log in:** POST `/login` with a correct password (`200`), a wrong one (`401`), and the pending instructor (`403`).
6. **Approve the instructor:** PUT `/updateStatus/{id}` with `{ "status": "ACTIVE" }`, then log in again (`200`).
7. **Deactivate a user:** PUT `/updateStatus/{id}` with `{ "status": "INACTIVE" }`, then log in (`403`).
8. **Reset a password:** PUT `/updateUser/{id}` with the full user body, then log in with the new password.
9. **Duplicate email:** register the same email again (`409`).

## 7. Differences from the SDD

The SDD's functional requirements (FR1 role-based login, FR2 approvals, account status and credential resets) are all covered. The data structure follows the group's existing code:

| SDD (ERD / class diagram) | Implementation | Reason |
|---|---|---|
| `USER` has no status column | `status` field (`PENDING`, `ACTIVE`, `INACTIVE`) | Needed by FR2; the ERD should be updated |
| `username` | `fullName` | Group's `User` entity already uses `fullName` |
| Separate `ADMIN`, `INSTRUCTOR`, `STUDENT` tables | One `users` table with `roleType` | Subtype entities were not implemented |
| Methods like `approveInstructorRegistration()`, `activateAccount()` | One `updateStatus` endpoint | Same features as a REST endpoint |
| No DTOs | `LoginRequest`, `StatusRequest` | Request bodies for login and status changes |

---

## 8. Known limitations

- Passwords are stored as plain text in `passwordHash` (no hashing yet).
- No login sessions or tokens: the frontend trusts `localStorage`, and the API doesn't check who is calling it.
- No audit log of admin actions.
